# CourseOS

CourseOS помогает методисту собрать курс: определить, чему научатся слушатели, распределить темы и часы, подобрать задания и проверить, помещается ли обучение в расписание. План, материалы и история изменений собраны в одном месте.

В репозитории — фронтенд приложения (`courseos/frontend`) и сервер CourseOS (`courseos/backend`). Сервер вызывает модели GigaChat и предоставляет единый API-эндпоинт агента `POST /api/v1/agent`: по запросу методиста строится каркас, а после его утверждения — комплект материалов (см. [«API агента»](#api-агента) — сразу ниже). Фронтенд можно запустить и без сервера: на готовых примерах весь сценарий работает в деморежиме без ключей.

Демо: https://tochka-sborki-2026-team-065.hub.gigaschool.ru

## API агента

Единый эндпоинт для автопроверки и внешних систем. Запрос проходит шаги агента с остановкой перед генерацией материалов — так же, как в интерфейсе:

1. **Разбор запроса** — сводка параметров (GigaChat-3-Pro, температура 0); явные числа из текста важнее ответа модели.
2. **Уточнения** — если не хватает типа программы или объёма либо двух и больше полей сводки, агент возвращает вопросы и не строит программу. Одно недостающее поле становится явным допущением. На содержательные вопросы модели без ответа методиста берётся рекомендованный вариант, и это видно в `assumptions`.
3. **Каркас** — цель, задачи, результаты, модули и темы от модели; часы по видам работы, итоговую аттестацию и связи считает код движка курса.
4. **Утверждение** — по умолчанию `approve: false`: сборка останавливается в `awaiting_approval`. Методист видит каркас, календарь, источники и замечания с идентификаторами. Через `/review` он явно применяет предложение или оставляет допустимое замечание с причиной. Каждое решение возвращает обновлённый каркас без генерации материалов. После проверки методист вызывает `/approve` с версиями и хешем; этот вызов сам ничего не исправляет и не отклоняет. При блокировках сборка остаётся в `awaiting_approval`.
5. **Материалы** — по вызову на тему, итоговый тест, итоговая аттестация и текстовые разделы программы, по два запроса параллельно.
6. **Самопроверка** — смысловая проверка комплекта моделью, затем доработка вопросов с ошибкой ключа; правила движка проверяют часы, покрытие результатов и разделы шаблона.
7. **Выгрузки** — DOCX, PPTX, Moodle XML, JSON и Markdown.

```sh
curl -X POST https://tochka-sborki-2026-team-065.hub.gigaschool.ru/api/v1/agent \
  -H 'Content-Type: application/json' \
  -d '{"request": "Нужна программа повышения квалификации на 72 часа «Анализ данных на Python» для сотрудников банков, очно-заочно, 4 недели. Итоговая аттестация — защита проекта."}'
```

| Метод | Назначение |
| --- | --- |
| `POST /api/v1/agent` | Собрать программу. Тело: `request` — текст запроса; `clarifications` — ответы на вопросы прошлого вызова свободным текстом; `answers` — ответы на содержательные вопросы (`{id или текст вопроса: ответ}`); `approve` (по умолчанию `false`; `true` — автоматический прогон); `wait` (по умолчанию `true`; `false` сразу возвращает `run_id` с кодом 202) |
| `GET /api/v1/agent/runs/{run_id}` | Состояние сборки и ход шагов |
| `POST /api/v1/agent/runs/{run_id}/review` | Разобрать одно замечание. Тело: `skeleton_version`, `skeleton_hash`, `course_version` и `decision: {action: "apply_finding", issue_id}` либо `decision: {action: "dismiss_finding", issue_id, reason}`. Возвращает новый каркас для проверки |
| `POST /api/v1/agent/runs/{run_id}/approve` | Утвердить проверенный каркас и собрать материалы. Тело: `skeleton_version`, `skeleton_hash`, `course_version`. Значения берутся из актуального `skeleton.version`, `skeleton.hash`, `skeleton.course_version`. Устаревшие версии отклоняются с 409 |
| `POST /api/v1/agent/runs/{run_id}/retry` | Продолжить прерванную сборку или повторить несозданные части. Готовые ответы используются из сохранённого результата; утверждение методиста сохраняется |
| `GET /api/v1/agent/runs/{run_id}/files/{имя}` | `program.docx`, `slides.pptx`, `test-moodle.xml`, `course.json`, `rationale.md` |

Для автопроверки можно явно передать `"approve": true` в исходном запросе: агент самостоятельно применит доступные исправления и снимет допустимые блокировки. Это **не утверждение человеком**: `approval.human_approved` останется `false`, событие называется `automatic_approval`, решения записываются от имени `automatic-api`. В выгрузках такой каркас остаётся неутверждённым методистом; JSON содержит `status.approved: false` и `approvals[].kind: "automatic"`.

Пример утверждения после проверки каркаса (подставьте актуальные значения из ответа):

```json
{"skeleton_version": 2, "skeleton_hash": "хеш из skeleton.hash", "course_version": 3}
```

Для `/review` передайте те же поля и явное решение, например:

```json
{"skeleton_version": 1, "skeleton_hash": "хеш из skeleton.hash", "course_version": 1, "decision": {"action": "dismiss_finding", "issue_id": "идентификатор из skeleton.audit_issues", "reason": "Методист проверил применимость профстандарта к программе"}}
```

Для редактирования каркаса передайте в `/review` `decision: {action: "save_skeleton", skeleton: <полный изменённый skeleton.document>}` с актуальными версиями. Часы и зависимости валидирует существующий движок; изменение каркаса сбрасывает утверждение и помечает материалы устаревшими.

Для точечной правки материала используйте `/review` с `decision: {action: "edit_material", change: <ChangeInput>}`: тот же предпросмотр и применение правки, что в интерфейсе. Для вопроса передаются `type: "question"`, `target_id`, `request`, `replacement`, `options`, `correct_index` (с нуля), `explanation`, `manual: true`. Ручная правка создаёт версию и делает самопроверку устаревшей; повторите её перед решением по блокерам.

После каждого `/review` заново проверьте ответ и используйте его версии в следующем запросе. Сборка и решения сохраняются на диск и восстанавливаются после перезапуска. `/review` доступен также для замечаний к готовым материалам: передайте актуальные версии из `skeleton` и `decision: {action: "dismiss_finding", issue_id, reason}`. Укажите в причине, что проверено, принято ли исправление или осознанно оставлен риск. В JSON сохраняются версия комплекта, исходная находка, автор, дата и обоснование; выгрузки обновляются.

В ответе: `status` (`awaiting_clarification`, `awaiting_approval`, `succeeded`, `needs_review` — комплект собран, но разделы или источники ждут методиста, `blocked`, `failed`), `questions`, `parameters` и `corrections`, `skeleton` (результаты и учебный план с часами), `assumptions`, `decisions`, `generation` (расход, сбои, самопроверка), `audit`, `checklist` (общие требования кейса и чек-лист запроса), `files`, `events` (время каждого шага от начала) и `usage` — вызовы модели с токенами и рублями. Сборки выполняются по одной; результаты хранятся в `courseos/backend/var/runs/`.

Состояние новых запусков сохраняется атомарно после каркаса, решений методиста и во время генерации. После перезапуска ожидающий утверждения каркас остаётся доступным для `/review` и `/approve`; прерванная сборка получает статус `failed` с причиной `failure.code: interrupted` и продолжается через `/retry`. Ранее созданные запуски без контрольной точки восстановить нельзя.

При частичном сбое готовые материалы доступны, а `generation.failed` перечисляет несозданные части. В интерфейсе появляется кнопка «Повторить незавершённые шаги». Повтор не вызывает модель для завершённых шагов с теми же входами; после изменения материалов самопроверка выполняется заново. Ручные правки сохраняются. Для ошибок запуска `failure` содержит `code`, `message`, `retryable` и `action`: при перегрузке или лимите нужно повторить позже, при отказе хранилища — восстановить запись на диск. Ошибка одной сборки не останавливает очередь остальных.

Движок курса для сервера собирается из фронтенда командой `npm run build:agent` (входит в `npm run build`) в `courseos/frontend/dist-agent`; путь можно переопределить переменной `AGENT_BUNDLE`.

### Время и стоимость (замер на ВМ, 17.10.2026)

Запрос из примера выше: ДПП ПК на 72 часа, GigaChat-3-Pro через шлюз хакатона. Время и стоимость шагов каркаса взяты из первого, некэшированного прогона того же запроса, материалов — из прогона, где каркас уже был в кэше. Сборка завершилась статусом `needs_review`: комплект и все пять файлов готовы, разделы ждут вычитки методистом.

| Этап | Время | Вызовов модели | Стоимость |
| --- | --- | --- | --- |
| Каркас: разбор, уточняющие вопросы, структура, часы | ≈ 20 с (по ТЗ — до 3 мин) | 3 | ≈ 0,85 ₽ |
| Материалы, самопроверка и выгрузки после утверждения | ≈ 62 с | 16 | 4,84 ₽ |
| **Полный комплект на 72 часа** | **≈ 1,5 мин** (по ТЗ — до 20 мин) | 19 | **≈ 5,7 ₽** |

Каркас на 40 часов отдельным прогоном собрался за 19 с и стоил 0,78 ₽. Время каждого шага возвращается в `events`, стоимость — в `usage`; журнал всех вызовов ведётся в `courseos/backend/var/llm-calls.jsonl`.

## Что можно сделать

- **Собрать план курса.** Указать аудиторию, цель, длительность и ограничения, затем уточнить недостающие детали.
- **Связать обучение с результатом.** Посмотреть на карте, какие темы и задания помогают освоить каждый навык и как он проверяется.
- **Проверить нагрузку.** Найти расхождения в часах и расписании до утверждения плана.
- **Посмотреть материалы.** Открыть демонстрационные конспекты, тесты, практические задания, проект и содержание слайдов.
- **Внести согласованные правки.** Сначала увидеть, что затронет изменение, затем применить его и сравнить версии.
- **Скачать результат.** Программа по шаблону АЦР в DOCX, слайды лекций в PPTX, тесты для LMS в Moodle XML, полные данные версии в JSON и обоснования решений в Markdown.

Решение об утверждении программы принимает методист. Приложение показывает, на чём основаны предложения и что ещё нужно проверить.

## Как запустить

Понадобятся Node.js версии 22.12 или новее и npm. В терминале, из корня репозитория:

```sh
cd courseos/frontend
npm ci
npm run dev
```

Откройте [http://127.0.0.1:5173](http://127.0.0.1:5173). Чтобы остановить приложение, нажмите `Ctrl+C` в терминале.

Публичное демо работает на сервере CourseOS (`courseos/backend`). Он раздаёт собранный фронтенд на `0.0.0.0:8000` и обращается к модели GigaChat. Серверу нужен Node.js 22.18 или новее:

```sh
cd courseos/frontend && npm ci && npm run build
cd ../backend && npm ci --omit=dev && npm start
```

Адрес и ключ LLM-шлюза сервер берёт из переменных `OPENAI_BASE_URL` и `OPENAI_API_KEY`; на ВМ хакатона `npm start` подхватывает их из `/opt/hackathon/ai.env`. Без них приложение работает в деморежиме, а разбор запроса моделью недоступен. Журнал вызовов модели и кэш ответов сохраняются в `courseos/backend/var/`, в git они не попадают.

## С чего начать

Для первого знакомства подойдёт пример **«Первые шаги в Python»** — курс на 16 часов для школьников без опыта программирования.

1. Выберите пример на главной странице. Посмотрите, как заполнены цель, аудитория и условия обучения, затем отправьте запрос.
2. Откройте план: проверьте результаты обучения, темы, задания и распределение часов.
3. В разделе **«Проверка и утверждение»** разберите замечания. В блоке **«Почему курс устроен так»** выберите раздел и решение: в карточке показаны объяснение и следующий шаг. Здесь же можно найти нужное пояснение и скачать Markdown ещё до утверждения.
4. Отметьте проверку и нажмите **«Утвердить программу»**. После этого перейдите к материалам курса.
5. Попробуйте **«Согласованные правки»**: опишите изменение, посмотрите его влияние и примените предложенный план. Если меняется основа программы, её нужно утвердить снова.
6. Сравните версии и откройте **«Выгрузки»** в материалах, чтобы скачать Markdown или JSON.

Есть и другие примеры: ИИ для учителей, анализ данных для сотрудников банков, кибербезопасность и DevOps. В примере с кибербезопасностью нужно уточнить неполный запрос. В DevOps заложен конфликт: 256 часов не помещаются в 8 недель при нагрузке до 4 часов в день. На нём удобно посмотреть, как приложение предлагает пересмотреть сроки или нагрузку.

## Как работает деморежим

Пять готовых примеров модель не вызывают и всегда строятся одинаково: их материалы подготовлены заранее. Для своего запроса параметры, каркас и после утверждения материалы пишет модель (см. ниже). Часы, связи и проверки во всех случаях считает код, а материалы остаются черновиками для проверки методистом.

### Работа с моделью

Сервер CourseOS вызывает модели GigaChat через OpenAI-совместимый шлюз хакатона. Модель и её параметры подбираются под шаг агента; маршруты описаны в [`models.ts`](courseos/backend/src/llm/models.ts).

- **Разбор запроса.** При первом нажатии «Отправить» текст методиста уходит в GigaChat-3-Pro с нулевой температурой, а параметры программы возвращаются в JSON и заполняют сводку. Кнопка отправки становится ✓: повторное нажатие подтверждает параметры. Ответ проверяется схемой, а явные числа из текста важнее ответа модели: если модель ошиблась в объёме часов или подставила форму обучения, которой в запросе нет, код это исправляет и сообщает. Методист всё равно сверяет и подтверждает сводку сам.
- **Уточняющие вопросы.** После подтверждения сводки GigaChat-3-Pro задаёт до четырёх вопросов по содержанию: инструменты, данные, итоговый проект, акценты. Для каждого вопроса модель объясняет, что от ответа зависит, предлагает варианты и рекомендует один из них; методист может ответить своими словами. Незаполненные поля сводки (входной уровень, форму обучения и т. п.) спрашивает само приложение на том же шаге. Ответы передаются модели при проектировании каркаса.
- **Каркас программы.** Если вопросов нет и сводка полная — сразу после подтверждения, иначе — после ответов на уточняющие вопросы GigaChat-3-Pro предлагает цель, задачи, результаты обучения с критериями, модули и темы. Для каждой темы модель указывает тип (вводная, отработка инструмента, проектная) и трудоёмкость от 1 до 5, но не часы: часы по видам работы распределяет код, поэтому сумма всегда равна подтверждённому объёму. Код также убирает ссылки на несуществующие результаты и темы, удаляет итоговую аттестацию, если модель предложила её темой, и сообщает о результатах, которые не формирует ни одна тема. Структура сохраняется во вводных курса: при смене объёма каркас пересобирается из неё без нового вызова модели. На странице плана видно, что каркас предложен моделью, и сколько это стоило. Если модель недоступна или ответила не по схеме, методист видит ошибку и может построить каркас по шаблону.
- **Материалы.** После утверждения каркаса GigaChat-3-Pro пишет материалы по частям: по вызову на тему (пункты лекции, практикум и самостоятельная работа для рабочей программы, 3–5 слайдов с заметками для преподавателя, практическое задание с критериями, вопросы текущего контроля), отдельно итоговый тест (не меньше 10 вопросов, каждый привязан к результату обучения) и итоговую аттестацию по образцу АЦР (требования, пример задания, критерии на 100 баллов, порядок защиты, на стажировке — вопросы собеседования с руководителем по каждому модулю). Часы, связи и id материалов остаются из утверждённого каркаса. Ответы приходят по JSON-схеме (structured output шлюза); ключи тестов, коды результатов и сумму баллов проверяет код. Запросы идут по два параллельно; если тема не сгенерировалась, она остаётся заготовкой, а причина видна над материалами.
- **Самопроверка.** Последний шаг: GigaChat-3-Pro читает тексты программы, задания с критериями, слайды, вопросы с объяснениями и ищет смысловые ошибки — неверные ключи тестов, темы не по уровню слушателей, обещания сверх объёма, недоступные в России инструменты. Вопросы с ошибкой ключа и результаты без вопросов исправляет отдельный шаг доработки теста, переписанный тест проходит повторную проверку. Во вкладке материалов можно повторить самопроверку после ручных правок. Через API используйте `/review` с `decision: {action: "recheck_materials", issue_id: "quality"}` и актуальными версиями. Серьёзная находка остаётся блокером готовности до явного решения методиста, даже если модель больше её не находит. Решение действует только для проверенной версии материалов. Неполная, неуспешная и устаревшая проверка не даёт готовность. Рассуждающая модель для этого шага пробовалась: на комплекте 72 ч она дважды истратила все 4096 токенов на рассуждение и вернула пустой ответ.
- **Учёт расхода.** Каждый вызов записывается в журнал: шаг, модель, токены, время и стоимость по ценам шлюза. Под результатом разбора и на странице плана видны модель, число токенов, время ответа и стоимость, а `GET /api/llm/usage` возвращает расход за текущие московские сутки по шагам.
- **Лимиты шлюза.** Сервер держит не больше двух одновременных запросов, повторяет запрос после сбоя или ответа 429 и сохраняет ответы: одинаковый запрос второй раз не оплачивается. Ошибки модели показываются пользователю; заполненные поля при этом не меняются.

### Параметры запроса и расписание

- Перед построением программы показывается редактируемая сводка параметров. Если текст примера изменён, параметры нужно сверить и подтвердить вручную; явные расхождения часов и недель блокируют отправку.
- Подтверждение календаря сохраняет заданный дневной лимит. Нехватка вместимости видна заранее, а изменение лимита оформляется отдельным решением и требует нового утверждения.
- Вместимость и расписание — разные проверки. В примере с Python расписание готово: восемь занятий по два часа по средам и субботам в течение четырёх недель. В остальных программах занятия назначаются в календаре вручную, иначе приложение показывает, что расписания нет.

### Замечания и исключения

- Принятое исключение хранит исходное замечание, причину и область действия — в версии, JSON и Markdown.
- Исключение не превращает непроверенное соответствие в пройденное и не отменяет арифметику часов или обязательные ограничения.
- После изменения структуры программы область исключения проверяется заново.

### Материалы

- Банковские практикумы используют связанные синтетические таблицы `clients` и `loans` с датами, сегментами и просрочкой. Условия и ожидаемые значения видны в материале.
- Предметные вопросы подготовлены для примеров с Python, банковской аналитикой, учителями и кибербезопасностью; для DevOps — предметные собеседования. Для своего запроса тест и задания пишет модель после утверждения каркаса.
- Из вопроса, задания или слайда открывается редактор полей: видны изменения и зависимости, сохранение создаёт новую версию. Ручные правки защищены от перезаписи; исправление ключа меняется и в JSON, и в Markdown. Изменение критериев оценивания или связей требует нового утверждения.
- Все материалы требуют предметной вычитки.

### Разделы программы и выгрузки

Во вкладке **«Разделы программы»** видны поля образца АЦР. Раздел с повторами текста или незаполненными полями считается незавершённым. Структурная полнота не подтверждает предметную или нормативную экспертизу.

Готовность каждого формата показывается отдельно во вкладке **«Выгрузки»**:

- **DOCX** — программа по шаблону АЦР: титул с пустыми реквизитами приказа, учебный план с модулями и темами 1.1, 1.2, рабочие программы, тесты с ключами, задания и критерии. Неподтверждённые источники вынесены в отдельный помеченный список.
- **PPTX** — слайды лекций по темам, пояснения преподавателя в заметках докладчика.
- **LMS** — тесты в формате Moodle XML: категория на тест, вопрос с одним верным ответом, объяснение ключа и тег с кодом результата обучения. Файл импортируется в банк вопросов Moodle и совместимых LMS.
- **JSON** — полная версия курса: каркас, материалы, аудит, расход модели и самопроверка.
- **Markdown** — программа с обоснованиями решений.

### Профессиональные стандарты

В сборку входит локальный каталог четырёх профстандартов:

| Код | Профстандарт |
| --- | --- |
| 01.001 | Педагог |
| 06.042 | Специалист по большим данным |
| 06.033 | Специалист по защите информации в автоматизированных системах |
| 06.026 | Системный администратор информационно-коммуникационных систем |

Полные тексты, редакции, ссылки на приказы Минтруда, источники, дата получения и SHA-256 хранятся в [`catalog.json`](courseos/frontend/src/entities/course/model/professional-standards/catalog.json). Тексты получены 15 октября 2026 года из открытых копий ГАРАНТ и Контур.Норматив; актуальность редакции и применимость проверяет методист. Серверная база не подключена: выбранный текст сохраняется вместе с курсом в браузере.

Чтобы сменить документ, нажмите в плане программы **«Изменить профстандарт»** и выберите стандарт из каталога, вставьте свой текст с названием и ссылкой или выберите **«Без профстандарта»**. Сохранение создаёт новую версию, сбрасывает связи результатов с прежним документом и требует повторного утверждения; прочие источники сохраняются.

Наличие текста профстандарта не означает, что программа покрывает всю квалификацию. В примерах с банковской аналитикой и DevOps стандарты используются только как кандидаты для части трудовых функций.

### Источники

Сервер извлекает текст PDF и DOCX (файл до 8 МБ, первые 100 страниц PDF, без OCR). В генерацию передаётся до 12 000 символов каждого из 20 источников вместе с названием, ID, URL и областью проверки. Интерфейс показывает исходный и переданный объём, обрезание, предупреждения и ошибки извлечения. Для вставленного вручную текста действует тот же лимит передачи.

`POST /api/sources/extract {name, base64}` извлекает текст, `POST /api/sources/check {url, claim?, excerpt?}` проверяет доступность публичного HTTP(S) URL и наличие указанного фрагмента. Сохраняются исходная и конечная ссылка, дата, HTTP-статус, утверждение, найденный фрагмент или причина невозможности проверки. Доступная страница без фрагмента не подтверждает утверждение. Даже найденная цитата требует проверки применимости методистом; автоматическая проверка не присваивает источнику достоверность. Ссылки модели проверяются при генерации и сохраняются в `generation.source_checks`; доступность и содержание показаны отдельно в материалах.

`GET /api/version` показывает коммит запущенного сервера и SHA-256 страницы сборки для сверки демо с отправленной версией.

### Хранение данных

Курсы, версии и решения сохраняются в браузере и остаются после перезагрузки страницы.

- Открывайте приложение по одному адресу: `localhost` и `127.0.0.1` используют разные хранилища.
- Перед очисткой данных браузера или нажатием **«Сбросить демоданные»** скачайте архив в блоке **«Хранилище и история»** на главной или во вкладке выгрузок. Архив включает все версии и невосстановленные данные.
- История не сокращается автоматически. После 15 версий приложение предлагает скачать архив и вручную удалить старые неутверждённые версии; утверждённые версии сохраняются всегда.
- Формат хранилища версионирован: совместимые данные прежнего формата мигрируют при открытии. Повреждённый курс изолируется, его исходные данные можно скачать, остальные курсы остаются доступны.
- Если квота браузера исчерпана, неудачная запись не затирает прежнее хранилище.

## Подключение сервера

Во фронтенде предусмотрен режим `live` для работы с внешним API курсов. Сервер CourseOS из `courseos/backend` этот контракт не реализует: он вызывает модель и предоставляет [API агента](#api-агента), а курсы в интерфейсе хранятся в браузере.

Создайте файл `.env.local` в папке `courseos/frontend` по образцу `.env.example`:

```dotenv
VITE_COURSE_MODE=live
VITE_COURSE_API_URL=/api/v1
```

Укажите адрес своего API и перезапустите приложение. Режим также можно переключить в верхней панели; выбор сохраняется в браузере. Если сервер недоступен, приложение покажет ошибку подключения.

Сервер должен поддерживать [контракт фронтенда](courseos/frontend/src/entities/course/api/contract.ts) и авторизацию через cookie. Если он работает на другом адресе, потребуется настройка CORS. Ключи языковых моделей храните на сервере: переменные `VITE_*` доступны в браузере.

## Для разработки

Фронтенд написан на React и TypeScript, собирается через Vite. Для форм используются React Hook Form и Zod, для запросов — TanStack Query. Проверки написаны на Vitest и Playwright.

Основные папки внутри `courseos/frontend`:

| Папка | Что внутри |
| --- | --- |
| `src/app` | Оболочка приложения, навигация и общие стили |
| `src/pages` | Создание курса, план, карта результатов, материалы и сравнение версий |
| `src/entities` | Данные курса, правила проверок и работа с API |
| `src/features` | Загрузка источников, правки и выгрузки |
| `src/shared` | Общие компоненты, настройки и вспомогательные функции |
| `tests` | Проверки логики и сценариев в браузере |

Сервер лежит в `courseos/backend`: `src/llm` — клиент шлюза с очередью, кэшем и журналом, `src/steps` — шаги агента, `src/server.ts` — HTTP API и раздача фронтенда. Тесты запускаются командой `npm test` и не тратят лимит модели: шлюз в них подменён. Во время `npm run dev` фронтенд проксирует `/api/llm` на сервер по адресу `http://127.0.0.1:8000`.

Команды выполняются из папки `courseos/frontend`:

```sh
npm run typecheck  # Проверить типы TypeScript
npm run lint       # Проверить форматирование исходников и тестов
npm test           # Запустить тесты логики
npm run build      # Проверить типы и собрать приложение в dist
```

Для браузерных тестов сначала запустите `npm run dev` в отдельном терминале, затем:

```sh
npm run test:e2e
```

По умолчанию используется Google Chrome, установленный в стандартную папку приложений macOS. Для другого расположения браузера укажите путь:

```sh
COURSEOS_BROWSER=/path/to/chrome npm run test:e2e
```

Готовую сборку можно посмотреть локально:

```sh
npm run preview -- --port 4173
```

Для размещения на хостинге используйте содержимое `dist`. Настройте сервер так, чтобы при прямом открытии внутренних страниц он возвращал `index.html`.

### Размещение на Vercel

В настройках проекта укажите **Root Directory** — корень репозитория (оставьте поле пустым). Файл `vercel.json` в корне задаёт установку зависимостей и сборку из `courseos/frontend`, каталог результата `courseos/frontend/dist` и открытие внутренних страниц через `index.html`.

После изменения настроек или добавления конфигурации запустите новый deployment. Если адрес по-прежнему возвращает `404 NOT_FOUND`, проверьте, что нужный production deployment успешно завершён и домен привязан к этому проекту в разделе **Settings → Domains**.
